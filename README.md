# وصّل الأجرة · Wassal El-Ogra

A casual puzzle game for mobile. You drive a Cairo microbus: collect fares as they are passed forward
seat by seat, hand back exact change before each passenger's stop, and save what you earn to furnish
an apartment and get married. It launches on Android in Egypt first, then the Gulf and iOS.

> **Status: design and planning.** There is no application code yet. The design documents and the
> project constitution are done. The first features to build are `M03` (app shell) and `B01`
> (backend skeleton).

## Planned layout

```text
apps/mobile/              Flutter app: screens, Flame trip scene, Rive characters
packages/trip_engine/     Pure-Dart gameplay engine (all trip rules live here)
packages/content_models/  Dart models generated from content/schemas
backend/                  Django 5.2 + DRF API, admin, Celery workers
tools/solver/             Python mirror of the engine: solver and trip generator
tools/speckit-extensions/ Project Spec Kit extensions (source)
contracts/openapi.yaml    API contract generated by the backend
content/schemas/          JSON Schemas for content packs
fixtures/parity/          Shared Dart ↔ Python engine fixtures
```

## Tech stack

- **Mobile:** Flutter (pinned with FVM), Flame, Rive, Riverpod, go_router, drift, dio.
- **Backend:** Python 3.13 with `uv`, Django 5.2 LTS, DRF, PostgreSQL 17, Redis/Valkey, Celery.
- **Infrastructure:** one ARM64 Oracle Cloud VM, Docker Compose, Caddy. Android CI on GitHub Actions,
  iOS builds on Codemagic (`codemagic.yaml`; Swift Packages, no CocoaPods). The
  [iOS test build runbook](docs/runbooks/ios-test-build.md) covers installing it on an iPhone.

## Ground rules

The full list is in the [constitution](.specify/memory/constitution.md). The ones that shape every
change:

- **One rules engine.** Trip rules live only in `packages/trip_engine` and its Python mirror. Any rule
  change ships with parity fixtures that pass in both Dart and Python.
- **Integer money.** All cash is integer piasters. Floats never hold money.
- **The server decides value.** Premium currency, purchases and entitlements are decided by the
  backend.
- **Offline first.** A regular trip is playable with no network.
- **Content is data.** Trips, prices and dialogue live in versioned content packs, never in code.
- **Arabic RTL first**, with minimum on-screen sizes treated as acceptance criteria.

## How work is done

Work is spec-driven with [Spec Kit](https://github.com/github/spec-kit) v1.2.1, run from Claude Code.

1. Each feature ID becomes one `specs/NNN-<short-name>/` folder and one git branch with the same name.
   Mobile features are `M01`–`M20` and backend features are `B01`–`B15`. A mobile/backend pair is
   planned together.
2. Each feature goes through
   `/speckit-specify` → `/speckit-clarify` → `/speckit-plan` → `/speckit-tasks` → `/speckit-analyze`
   → `/speckit-implement`.
3. Two extensions handle branches:
   - `git` (Spec Kit core) creates the feature branch during `/speckit-specify`;
   - `feature-branch` (this repo, in `tools/speckit-extensions/`) checks that branch out before
     every later step, or creates it if it is missing. It never stashes or discards changes; if the
     switch is blocked, the step stops.
4. Features are built in the joint MVP order in
   [`docs/architecture-backend.md` §21](docs/architecture-backend.md), starting with `M03` + `B01`.

To change the `feature-branch` extension, edit its source and reinstall it:

```bash
specify extension add --dev tools/speckit-extensions/feature-branch --force
```
